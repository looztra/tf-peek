Use this skill whenever you produce a commit message or a pull request.

## Commit and PR title format

`type(scope): description` — the scope is **mandatory**. CI enforces it on the PR title with
`amannn/action-semantic-pull-request` (`requireScope: true`); a missing or unknown scope fails the
check and posts a bot comment.

- Types: `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Scope: the component or area touched. Pick an existing one — list them with
  `git log --pretty=%s -50` — and only invent a new scope for a genuinely new area.
- Description: imperative mood, lower case, no trailing period.
- `type(scope)!: …` or a `BREAKING CHANGE:` footer for breaking changes.

Releases are generated by release-please from merged commit subjects, and PRs are squash-merged, so
the PR title becomes the release-note line. Get the title right at PR level, not only in local
commits.

## Pull request description

Fill every section of `.github/PULL_REQUEST_TEMPLATE.md`. In this template family that means:

1. Link to the initial request/ticket — `Fixes #<issue_number>`, or `N/A` when there is no issue.
2. What this PR provides — bullet list; state *why*, not only *what*; link the ADR, design doc, or
   change proposal the work came from.
3. Breaking changes — `N/A` or an explicit list.
4. How to test — the exact commands a reviewer runs, plus the result you observed.

## Rules

1. One logical change per commit; keep generated artifacts (regenerated goldens, lock files) in the
   same commit as the change that caused them.
2. Never amend or force-push a branch you do not own.
3. The `python-quality-gates` checks must pass before opening or updating a PR.
